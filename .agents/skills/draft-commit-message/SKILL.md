# コミットメッセージ案の作成

現在の差分とチケット情報から、プロジェクト規約に沿ったコミットメッセージ案を作成する。メッセージ案の生成だけを行い、Gitの状態を変更しない。

## ワークフロー

### 1. コミット規約を確認する

リポジトリに `docs/develop/workflow/commit.md` があれば最初に読み、形式、粒度、表現、ステージングの規約をSSOTとして従う。参照できない場合は、適用できる規約を確認できないことを伝える。

### 2. 対象差分を決める

読み取り専用コマンドで、ブランチ名、`git status`、ステージ済み差分、未ステージ差分、未追跡ファイルを確認する。

- ステージ済み変更がある場合は、ステージ済み差分だけをコミット対象にする。
- ステージ済み変更がなく、作業ツリーに変更がある場合は、その変更を暫定的な対象とし、未ステージであることを明記する。
- ステージ済み変更と未ステージ変更が混在する場合は、未ステージ変更を案へ混ぜず、対象外として明記する。
- 未追跡ファイルは `git diff` だけでは内容を確認できないため、`git status` で存在を確認し、対象とする場合だけ内容を読む。
- 差分がない場合は、根拠のない案を生成せずに終了する。

秘密情報や個人情報を表示しない。疑わしいファイルは内容を読まず、対象に含まれる可能性だけを警告する。

### 3. チケットIDを確定する

次の優先順位でチケットIDを決める。

1. ユーザーが明示したJira IDまたはGitHub Issue番号
2. 現在のブランチ名から一意に読み取れるID
3. ユーザーが提供したチケットURLから一意に読み取れるID

複数のIDが競合する場合は推測せず、競合を示してユーザーへ確認する。IDを特定できない場合は、規約で省略が許される軽微な変更かを判断し、省略したことを明記する。チケットとの関連が必要な変更ではIDを捏造せず、確認を求める。

### 4. 変更の意図を要約する

ファイル名だけで判断せず、差分から外部に観測できる変更後の状態を一つの日本語句へ要約する。

- 現在形で、変更後に何ができるか、または何が変わるかを書く。
- 「修正する」「対応する」「更新する」だけの曖昧な表現を避ける。
- 実装手段より、履歴から追跡したい変更意図を優先する。
- 差分に存在しない効果、テスト結果、チケットの完了を主張しない。
- 一行で簡潔に書き、本文やConventional Commits形式を独自に追加しない。

差分に独立してレビュー・切り戻しできる複数の関心事が含まれる場合は、単一の案で覆い隠さず、コミット分割案と各メッセージ案を提示する。

### 5. 規約へ照合する

案を出す前に、次を確認する。

- SSOTが定める形式に一致する。
- チケットIDと変更内容の間に半角スペースがある。
- チケットIDが根拠と一致する。
- 変更内容が対象差分全体を過不足なく表す。
- 曖昧な表現だけで終わっていない。
- 一つの論理的な変更を表している。

## 出力形式

最初に推奨案をコピー可能なコードブロックで提示する。

```text
SCRUM-123 変更後の状態が分かる日本語
```

続けて、次を簡潔に記載する。

- 対象: `ステージ済み` または `未ステージ`
- チケットIDの根拠: ユーザー指定、ブランチ名、URL、または省略理由
- 要約の根拠: 案へ反映した主要な変更
- 対象外: 混在する未ステージ変更など。なければ `なし`

代替案は、変更意図に複数の妥当な表現がある場合だけ最大2件提示する。コミット分割が必要な場合は、推奨案の代わりに分割単位、対象ファイルまたは差分、各メッセージ案を提示する。

## 安全規則

- `git add`、`git commit`、`git commit --amend`、`git push`を実行しない。
- ファイル、Git設定、ブランチ、履歴を変更しない。
- ユーザーがコミット実行も明示的に依頼した場合でも、まず案を提示して確認可能にする。
- 秘密情報や個人情報をメッセージ案や根拠へ含めない。
