# プロジェクト設計クイズ

現在のリポジトリを根拠に4択問題を1問ずつ出題し、回答後に判定と解説を示す。正解や問題集をSkill内へ固定せず、確認済みの文書とソースコードから作成する。

## 1. 出題条件を決める

利用者が指定していない項目だけ確認する。回答がなくても進められる場合は、既定値を使用する。

- 分野：設計、アーキテクチャ、実装方針、テスト、運用規約など
- 難易度：`基礎`、`実践`、`設計判断`
- 問題数：既定では5問。利用者が終了を求めるまで続けてもよい

難易度は次の観点で選ぶ。

| 難易度 | 主な出題内容 |
| --- | --- |
| `基礎` | 用語、責務、レイヤー、明文化された方針 |
| `実践` | 変更箇所、処理の流れ、エラー分類、テスト方法 |
| `設計判断` | ADRなどに記録された選択肢、採用理由、トレードオフ |

難易度が未指定の場合は`基礎`を使用する。

## 2. 根拠を準備する

出題前にリポジトリの現在状態を確認する。全ファイルを毎問読み直さず、次の手順で対象を絞る。

1. ディレクトリ構成、索引、検索結果から、分野に関係する一次資料を2～4件選ぶ。
2. 文書の関連見出しと、ソースコードの型、関数、テストを確認する。
3. 確認した根拠から、正解が一意になる問題候補を3～5問準備する。
4. 同じセッションでは確認済みの根拠を再利用する。

次の場合は根拠を再確認する。

- 出題分野が変わった
- コンテキストが圧縮された
- 利用者が変更後のファイルを対象に含めた
- 根拠の内容または正解に確信が持てない

文書と実装が矛盾する場合は、その内容を問題にしない。不整合として利用者へ報告し、別の根拠を選ぶ。調査結果、決定済みの方針、実装済みの動作、未確認事項を区別する。

## 3. 問題を作る

各問題は次の条件を満たすように作る。

- 選択肢を4つにする
- 正解を1つだけにする
- 記憶だけでなく、設計理由または適用判断を確認できる内容を優先する
- 未決定事項、廃止済みの記述、根拠が競合する内容を正解にしない
- 表現の差だけで正誤が決まる選択肢を避ける

回答前は正解、解説、根拠の位置を示さない。問題番号、質問、4つの選択肢、回答方法だけを提示し、1問ごとに回答を待つ。

## 4. 回答を判定する

回答後は、次の順に簡潔に示す。

1. `正解`または`不正解`
2. 正しい選択肢
3. 正解となる理由
4. 他の3つの選択肢が不正解となる理由
5. 根拠1～3件
6. 現在の正答数と回答数

根拠には、リポジトリ相対パスと見出し、型、関数、または該当行を示す。行番号は確認時点の補助情報として扱い、内容を特定できる名前も併記する。推論を含む場合は、確認済みの事実と推論を分ける。

判定後は次の問題を出してよいか確認する。利用者が連続出題を指定した場合は、判定と解説の後に次の1問を提示する。

## 5. 終了する

利用者が終了を求めた場合、または指定した問題数に達した場合は、次を示す。

- 正答数、回答数、正答率
- 理解できていた分野
- 復習を推奨する分野
- 復習に使える主な文書またはソースコード

成績と出題履歴はセッション内だけで管理する。ファイル、データベース、外部サービスには保存しない。
