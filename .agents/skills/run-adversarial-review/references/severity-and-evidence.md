# 深刻度・根拠・出力基準

## 深刻度

| 深刻度 | 基準 |
| --- | --- |
| Critical | 情報漏えい、権限侵害、復旧困難なデータ損失、広範な停止など、直ちに変更を止める必要がある |
| High | 要件違反、主要機能の故障、発生可能性の高い回帰など、マージ前の対応が必要 |
| Medium | 限定条件での不具合、具体的な保守・運用リスク、重要なテスト不足がある |
| Low | 影響が限定的な正しさ、可読性、診断性の問題があるが、変更を直ちに止めるほどではない |

深刻度は影響度と発生条件から判定する。確信度の低さを深刻度で表現しない。好みやスタイルだけの違いは、ユーザーが要求しない限り指摘しない。

## 確信度

| 確信度 | 基準 |
| --- | --- |
| High | コード、実行結果、または一次情報から再現・確認できる |
| Medium | 根拠はあるが、環境や未確認の呼び出し条件に依存する |
| Low | 妥当な仮説だが、採否に追加の検証が必要 |

Lowの項目は確定した欠陥として扱わず、未確認事項または追加検証として報告する。

## 根拠の優先順位

リポジトリ内の主張は、次を優先する。

1. 対象のソースコード、テスト、設定
2. 実際のコマンド結果、ログ、再現結果
3. チケット、設計文書、プロジェクト規約
4. Git差分と履歴

外部の主張は、次を優先する。

1. 公式ドキュメント、標準仕様
2. 上流のソースコード、公式リリースノート
3. 原著論文、公式のセキュリティ情報

ブログ、掲示板、検索結果の要約は、一次情報の発見または補助にだけ使用する。一次情報が存在する場合、それらだけを根拠にしない。

## 指摘の採用条件

次をすべて満たす指摘だけを採用する。

- 対象箇所を特定できる。
- 期待する振る舞いと実際の振る舞いの差を説明できる。
- 具体的な入力、状態、操作などの故障条件を示せる。
- ユーザーまたはシステムへの影響を説明できる。
- コード、実行結果、仕様などの根拠を示せる。
- 呼び出し元の保証、既存の検証、別の仕様解釈など、自らの主張を否定し得る条件を調べている。

「問題になる可能性がある」だけの主張や、実在しない将来要件を前提にした主張は採用しない。

## 指摘の出力形式

```markdown
## [High] 指摘を端的に表すタイトル

- Location: `path/to/file:line`
- Confidence: High
- Classification: Fact | Inference | Unverified
- Problem: 期待する振る舞いと実際の振る舞いの差
- Failure Scenario: 問題が発生する具体的な入力、状態、操作
- Impact: ユーザーまたはシステムへの影響
- Evidence: コード、テスト結果、一次情報の参照先
- Falsification Attempt: 指摘が誤りとなる条件と、その確認結果
- Recommendation: 最小限の修正方針または追加検証
```

複数の場所が原因の場合を除き、`Location` は問題を修正すべき最小の行に置く。外部の一次情報は、確認できるURLまたは文書名と版を記載する。
