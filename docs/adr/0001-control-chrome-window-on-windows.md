# ADR-0001: WindowsでChromeウィンドウを起動・配置する

- Status: Accepted
- Date: 2026-07-20
- Related: SCRUM-11

## Context

MVPでは、Windows 11のプライマリディスプレイ上にGoogle Chromeの新しいウィンドウを1つ、指定した位置とサイズで起動します。

Chromiumには初期位置とサイズを指定する起動オプションがありますが、Chrome起動済み時の挙動、Windowsの表示倍率、ウィンドウ枠、OSやChromeによる補正を考慮する必要があります。起動要求が受け付けられたことだけでは、要求値どおりに配置されたことを確認できません。

## Decision Drivers

- Chrome未起動時と起動済み時の両方で新しいウィンドウを扱えること
- ユーザー単位とシステム単位の標準インストールを検出できること
- 要求した位置とサイズ、および実際の結果を区別できること
- プロファイル選択画面を通常のブラウザウィンドウと誤認しないこと
- 任意の実行ファイルや利用者由来のコマンドライン引数を実行しないこと
- Windows固有の詳細をInfrastructureへ隔離できること
- 自動テストと実機テストの責務を分けられること

## Considered Options

### Option 1: Chromeの起動オプションだけを使用する

`new-window`、`window-position`、`window-size`を指定してChromeを起動します。

利点:

- 実装が小さい
- Chrome自身の初期配置処理を利用できる

欠点:

- 実際の配置結果を確認できない
- Chrome起動済み時やDPI環境で指定値が反映される保証がない
- Chromeの非保証な起動オプションへ依存する

### Option 2: 起動後にWin32 APIだけで配置する

Chromeを起動し、新しいトップレベルウィンドウを識別してWin32 APIで移動・リサイズします。

利点:

- 配置要求と結果確認をWindows側で制御しやすい
- Chromeの位置・サイズ用起動オプションへの依存を減らせる

欠点:

- 対象ウィンドウの識別と待機処理が複雑になる
- DPI認識状態と座標系を明示的に扱う必要がある
- 他のChromeウィンドウを誤操作しない対策が必要になる

### Option 3: 起動オプションで初期配置し、Win32 APIで確認・補正する

Chromeへ初期位置とサイズを渡し、作成されたウィンドウをWin32 APIで識別して結果を確認します。必要な場合だけ再配置します。

利点:

- 初期配置をChromeへ伝えつつ、実際の結果も確認できる
- 差異が許容範囲内なら不要な再配置を避けられる

欠点:

- Option 1とOption 2の両方の複雑さと依存を一部持つ
- 許容差と補正条件を決める必要がある

## Decision

Option 3を採用します。

Chromeの検出には、Windowsの`App Paths`を優先し、標準インストール先をフォールバックとして扱います。`App Paths`から得たパスは正規化し、許可したChrome標準インストール先と一致する場合だけ採用します。Chromeのパスと固定した引数はアプリケーション側で構築し、利用者に実行ファイルや追加引数を指定させません。デジタル署名とリパースポイントの検証はSCRUM-27の対象外とし、必要性を後続作業で判断します。

探索順は、現在のユーザーの`App Paths`、システム全体の`App Paths`、ユーザー単位の標準インストール先、システム単位の標準インストール先とします。標準インストール先はWindowsのKnown Folder APIから組み立てます。許可範囲外、または存在しない`App Paths`の候補は採用せず、次の候補を探索します。レジストリまたはKnown Folder APIへのアクセス失敗は、Chrome未検出と区別します。

Chromeの起動コマンドはApplicationで構築し、起動引数を`--new-window`だけに固定します。Infrastructureは検出済みの実行パスと固定コマンドを使用してプロセスを開始し、Chromeの終了を待ちません。起動結果のプロセスIDは後続追跡の補助情報として扱い、配置対象のウィンドウをプロセスIDだけで確定しません。Chrome未検出、非対応OS、プロセス起動失敗はApplicationの結果として区別します。

製品実装の実機検証では、Chrome未起動時と通常ウィンドウ起動済み時の両方で起動要求が受け付けられ、プロファイル選択画面が1つ表示されました。利用者がプロファイルを選択すると、未起動時は通常ウィンドウが1つ表示され、起動済み時は通常ウィンドウが1つ増えました。

プロファイル選択画面がすでに表示されている状態で再度起動を要求した場合は、2つ目の選択画面が作成されず、既存の選択画面が前面へ移動しました。プロファイル選択画面は正常な中間状態として扱い、プロセス開始の成功だけで通常ウィンドウの作成完了または増加を判定しません。

起動オプションだけではプロファイル選択後の通常ウィンドウを要求位置へ配置できないため、追跡した通常ウィンドウをWin32 APIで確認・補正します。

Applicationの起動Workflowは、起動条件の事前検証、Chrome検出、起動前スナップショットを含む追跡開始、検出済みChromeの起動、通常ウィンドウの追跡、最終検証を含む二段階配置の順に実行します。検出した実行ファイルパスは、追跡、起動、配置で共有します。前段が失敗した場合は後続処理を実行しません。追跡開始後にChrome起動前の取消または起動失敗が発生した場合は、追跡Sessionを明示的に閉じます。Contextは追跡と配置へ伝播し、配置の安定待機中に取消または期限切れとなった場合は、後続の測定と移動を実行しません。

Chromeのプロファイル選択画面は正常な中間状態として許容します。アプリケーションはプロファイル情報を読み取らず、特定または最後に使用したプロファイルを自動選択しません。利用者による選択後に生成された通常のブラウザウィンドウを追跡し、そのウィンドウを確認・補正の対象にします。

特定の`profile-directory`を固定する方法は、利用者のChrome環境とChrome内部仕様への依存を増やすため採用しません。プロファイル選択の待機中は利用者が取り消せるようにし、60秒以内に選択されない場合はタイムアウトとして扱います。追跡方式と待機終了条件は、[ADR-0002](./0002-track-chrome-window-lifecycle.md)で決定しています。

実機検証では、Chromeの通常ウィンドウが起動済みの場合もプロファイル選択画面が表示されました。選択後に生成される通常のブラウザウィンドウを、遷移中の候補ハンドルと待機終了時の有効なハンドルから追跡します。

プロファイル選択後の通常ウィンドウへの置き換わりは、ネイティブウィンドウハンドルの消失と出現を追跡する方法で検出できました。目視確認でも通常のブラウザウィンドウであることを確認しました。一方、DPI 144の環境では`GetWindowRect`のDPI仮想化された値とDWMの物理座標が一致せず、起動引数だけでは要求したプライマリディスプレイ上の位置へ配置されませんでした。

検証では、呼び出しスレッドをPer-Monitor DPI Aware V2に設定し、プライマリディスプレイのDPIで要求値を物理座標へ変換しました。追跡した通常ウィンドウへ`SetWindowPos`を適用し、補正前後の値を同じDPI認識状態で比較しました。

一度の`SetWindowPos`でDPI 144のディスプレイからDPI 96のプライマリディスプレイへ位置とサイズを変更した結果、位置は要求どおりになりましたが、サイズは要求値のおよそ3分の2になりました。ChromeがDPI変更時にウィンドウサイズを再調整するため、異なるDPI間の補正は次の二段階で行う必要があります。

1. `MonitorFromPoint`と`GetMonitorInfo`で現在のプライマリモニターを取得する
2. サイズを維持してプライマリディスプレイへ移動する
3. `MonitorFromWindow`で対象モニターを確認し、対象ウィンドウのDPI変更と位置の安定を待つ
4. 移動後の`GetDpiForWindow`で得たDPIを使用し、要求位置とサイズを適用する

二段階補正の実機検証では、DPI 144のディスプレイに現れた通常ウィンドウをDPI 96のプライマリディスプレイへ移動し、DPI変更の安定後に要求値を適用しました。最終的な`GetWindowRect`は要求したX=100、Y=100、幅1000、高さ700と一致しました。

位置とサイズの成否は、Per-Monitor DPI Aware V2の呼び出し元から`GetWindowRect`で取得した外接矩形を基準に判定します。DWMの表示境界は不可視リサイズ境界を含まないため、診断情報として併記します。

## Consequences

- Windows固有のChrome検出、プロセス起動、ウィンドウ識別、座標取得をInfrastructureへ隔離する必要がある
- Application層では、要求した配置と実際の配置を別の値として扱う必要がある
- 単体テストではOS境界を差し替え、Windows実機では統合テストを行う必要がある
- 最終的な`GetWindowRect`が要求した外接矩形と一致しない場合は配置失敗として扱い、DWM表示境界は診断情報として使用する
- 候補の一意性とウィンドウハンドル、PID、プロセス開始時刻、ウィンドウクラスを各操作前に確認し、一意性または同一性を確認できない場合は補正しない
- 二段階補正の途中で失敗した場合は自動ロールバックせず、部分変更の有無、処理段階、最後に取得できた矩形を結果として返す

## Validation

- [x] Chrome未起動時に新しいウィンドウを識別できる
- [x] Chrome起動済み時に新しいウィンドウを識別できる
- [x] 100%の表示倍率で要求値と実測値を比較できる
- [x] 100%以外の表示倍率で要求値と実測値を比較できる
- [x] Chromeの探索順と異常系を自動テストで確認できる
- [x] 標準インストールされたChromeをWindows 11実機で検出できる
- [x] Chrome未起動時に製品実装から新しいウィンドウを要求できる
- [x] Chrome起動済み時に製品実装から新しいウィンドウを要求できる
- [ ] ユーザー単位とシステム単位のChromeが共存するWindows 11実機で優先順位を確認できる
- [x] プロファイル選択画面と通常のブラウザウィンドウの扱いを決定できる
- [x] プロファイル選択後の通常のブラウザウィンドウを追跡できる
- [x] DPI認識状態をそろえて通常ウィンドウをプライマリディスプレイへ補正できる
- [x] 検証結果に基づいて最終案を決定できる
