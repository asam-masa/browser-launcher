# ADR運用ガイド

## 目的

Architecture Decision Record（以下、ADR）は、重要な設計判断の背景、候補、採用理由、影響、検証方法を記録するために使用します。結論だけでなく、同じ状況で判断を再検討できる根拠を残します。

## ADRを作成する基準

次のいずれかに該当する場合は、ADRの作成を検討します。

- 複数の妥当な設計候補がある
- 複数レイヤー、外部境界、運用、または後続作業へ影響する
- 判断の制約やトレードオフを後から参照する必要がある
- 既存ADRのDecisionを置き換える、または重要な補足を加える

局所的で容易に変更できる実装詳細は、コードコメントまたはPR本文へ記録します。すべての設計判断をADRにしません。

## 決定までの手順

1. 解決する問い、対象範囲、対象外、制約を明確にする
2. 既存ADR、関連文書、コード、設定、テストを確認する
3. 外部仕様に関する事実を一次情報で確認する
4. Decision Driversを定める
5. 複数候補を同じ基準で比較する
6. 各候補の利点、欠点、リスク、検証方法を整理する
7. 推奨案と根拠を提示する
8. 依頼者が候補を選択した後にDecisionを確定する

承認前の推奨案は提案であり、Decisionではありません。未確認情報を事実として記載せず、判断へ与える影響と確認方法を示します。

## ADRの構成

新しいADRは`docs/adr/`へ配置し、次の構成を使用します。

```markdown
# ADR-<番号>: <タイトル>

- Status: <Status>
- Date: <日付>
- Related: <関連チケットまたは資料>

## Context

## Decision Drivers

## Considered Options

## Decision

## Consequences

## Validation

## References
```

各項目には次を記載します。

| 項目 | 内容 |
| --- | --- |
| `Context` | 背景、解決する問い、対象範囲、制約、確認できた事実 |
| `Decision Drivers` | 候補を比較する共通の判断基準 |
| `Considered Options` | 各候補の概要、利点、欠点、リスク |
| `Decision` | 承認された候補と採用理由 |
| `Consequences` | 利点、欠点、追加責務、移行、運用、後続作業への影響 |
| `Validation` | 判断の検証方法と、実施済み・未実施の結果 |
| `References` | 判断の根拠に使用した一次情報と関連資料 |

参照資料がない場合も`References`を省略せず、`なし`と記載します。この規則は新しいADRへ適用し、既存ADRを一括変更しません。

## メタデータ

ADR番号、日付、Status、Relatedは、チケットまたは依頼者の指示で確定します。既存ADRの最大番号、現在日付、会話の流れから推測して補いません。

値が未指定の文書案では`<未指定>`と記載します。ADRをファイルへ保存する前に、番号、タイトル、日付、Status、Related、保存先を確認します。

既存ADRを置き換える場合は、元のADRを削除せず、Statusと後続ADRへの参照を更新する方針について個別に合意します。

## 事実と判断の扱い

- リポジトリ内の事実は、コード、設定、テスト、要件、既存ADR、実行結果を根拠にする
- 外部仕様に関する事実は、公式ドキュメント、標準仕様、原著論文などの一次情報で確認する
- 確認済みとの申告だけでなく、資料名とリンクまたは提供内容、裏付ける主張の対応を記録する
- 事実、事実から導いた推論、判断、未確認事項を区別する
- 候補を同じDecision Driversで比較し、採用案だけを有利に記述しない
- 確認していない検証を完了済みとして記載しない

## 文書案と保存

ADR案の作成と、`docs/adr/`へのファイル保存を区別します。AIエージェントは、最初にチャット上で比較結果とADR案を提示します。ファイルを保存する場合は、パス、メタデータ、内容、影響を示し、依頼者の承認を得ます。
