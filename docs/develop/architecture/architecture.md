# アーキテクチャ方針

## 目的

本ドキュメントは、Go・React・DDD・クリーンアーキテクチャを本プロジェクトへ適用する際の判断基準を定めます。

原則を形式的に適用することではなく、変更理由を説明でき、テストしやすく、機能追加に伴う影響範囲を限定できる設計を目的とします。

## 基本方針

- ドメインのルールをフレームワーク、UI、OS、永続化の詳細から分離する
- 依存関係は、詳細を扱う外側から方針を扱う内側へ向ける
- 一つのモジュールや型には、変更する理由を一つだけ持たせる
- 抽象化は、実際に存在する境界や差し替えの必要性に対して導入する
- 将来の可能性だけを理由に、インターフェースやレイヤーを増やさない
- 設計上の例外は許容するが、理由と影響をPRへ記録する

## レイヤーと責務

概念上、次のレイヤーへ分けます。ディレクトリを必ず一対一で対応させる必要はありません。

| レイヤー | 主な責務 | 依存してよい対象 |
| --- | --- | --- |
| Domain | エンティティ、値オブジェクト、ドメインルール | 原則として標準ライブラリのみ |
| Application | ユースケースの実行、処理の調整、トランザクション境界 | Domain |
| Interface Adapter | HTTP、IPC、画面入力などの変換 | Application、Domain |
| Infrastructure | OS、ブラウザ、ファイル、DB、外部サービスとの接続 | 内側で定義された契約 |
| UI | 表示、ユーザー操作、画面固有の状態 | 公開されたApplicationの契約 |

### Domain

- 業務・アプリケーション上の不変条件を表現する
- UI表示用の文言、JSON、データベース、OSコマンドの都合を持ち込まない
- 値に制約がある場合は、プリミティブ型のまま扱わず値オブジェクトを検討する
- 常に有効な状態を保てるよう、生成時または状態変更時にルールを検証する

すべてのデータをエンティティや値オブジェクトにする必要はありません。振る舞いや不変条件を持たないデータは、単純な構造体で表現します。

### Application

- 一つのユースケースとして、ドメインと外部機能を調整する
- HTTP、React、特定のDBなど、呼び出し方法や技術詳細へ依存しない
- 認可や処理順序など、ユースケース固有のルールを扱う
- 外部機能が必要な場合、利用側で最小限のインターフェースを定義する

### Interface Adapter・Infrastructure

- 外部から受け取った値を、ApplicationやDomainが扱える形式へ変換する
- Domainの値を、外部API、OSコマンド、永続化形式へ変換する
- 外部ライブラリやOS固有のエラーを内側へそのまま漏らさない
- OS固有の実装は、可能な限り共通の契約の背後へ隔離する

### UI

- Reactコンポーネントは表示とユーザー操作を担当する
- ドメインルールをコンポーネント内へ重複実装しない
- 画面固有の入力検証と、ドメイン上の不変条件を区別する
- Goとの通信形式はDTOとして扱い、Domainの型と同一視しない

## 依存関係のルール

```text
UI / Infrastructure / Interface Adapter
                  ↓
             Application
                  ↓
                Domain
```

- DomainからApplication、Infrastructure、UIを参照しない
- Applicationから具体的なInfrastructure実装を参照しない
- 外側の都合を内側へ渡す場合は、内側で必要な情報だけを持つ型へ変換する
- 循環依存が発生した場合は、責務または境界が不明確になっていないか見直す

## インターフェースの方針

- インターフェースは原則として利用する側のパッケージで定義する
- 一つの実装しかなく、差し替えや境界分離の必要もない場合は、具象型を使用する
- テストでモックを作ることだけを目的に、広いインターフェースを定義しない
- 呼び出し側が必要とする最小限のメソッドだけを含める
- 外部ライブラリのAPIをそのままプロジェクト全体へ公開しない

## DTOとドメインモデル

- DTOは、UI、通信、永続化など境界を越えるデータ形式として使用する
- Domainの型は、不変条件と振る舞いを表現するために使用する
- 境界で明示的に変換し、外部仕様の変更がDomainへ直接波及しないようにする
- 単純なデータまで機械的に二重定義せず、分離による利益がある場合に適用する

## 設計変更の進め方

重要な設計判断の比較と記録には、[ADR運用ガイド](./architecture-decision.md)を使用します。

1. 解決する課題と受け入れ条件を確認する
2. 影響する責務とレイヤーを特定する
3. 最小の設計案と代替案を比較する
4. 依存方向とテスト方法を確認する
5. 小さな実装単位へ分割する
6. 重要な判断はPR、必要に応じてADRへ記録する

## 採用するアプリケーション構成

デスクトップアプリケーション基盤とGo・React間の連携方式は、[ADR-0003](../../adr/0003-use-wails-v2-for-desktop-foundation.md)に従います。

製品用Wailsプロジェクトはリポジトリ直下へ配置します。Wails標準の生成処理とコマンドを単純に保ち、単一の製品アプリケーションに不要な階層を増やさないためです。

```text
browser-launcher/
├── main.go
├── internal/
│   ├── application/
│   ├── adapter/
│   ├── domain/
│   └── infrastructure/
└── frontend/
    └── src/
```

`domain`と`infrastructure`は概念上の配置先です。責務を持つコードが存在するまで、空のパッケージや差し替え用途のないインターフェースは作成しません。

Wailsへ公開するControllerとDTOは`internal/adapter/wails`へ配置します。Reactは生成されたTypeScriptバインディングを使用し、Applicationの型やDomainの型を直接参照しません。

利用者が論理ピクセルで入力したChrome起動条件は、[ADR-0004](../../adr/0004-validate-launch-bounds-against-primary-work-area.md)に従って物理座標へ変換し、Windowsの使用可能領域と比較します。Windows APIとDPI認識状態の操作はInfrastructureへ隔離し、Domainは同じ座標系にある矩形の内包関係だけを扱います。

## 設計レビューのチェックリスト

- [ ] ドメインルールが技術詳細から分離されている
- [ ] 依存関係が内側へ向いている
- [ ] 各型・パッケージの責務を説明できる
- [ ] 境界を越えるデータ変換の場所が明確である
- [ ] エラーを変換する場所が明確である
- [ ] 重要な振る舞いを自動テストできる
- [ ] 現在必要のない抽象化を導入していない
- [ ] より単純な設計を採用しない理由を説明できる
