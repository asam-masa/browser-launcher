# エラー・ログ方針

## 目的

エラーを適切な責務で扱い、利用者には次の行動が分かる情報を、開発者には原因を調査できる情報を提供します。同時に、秘密情報や実装詳細が意図せず公開されることを防ぎます。

## 基本原則

- エラーを握りつぶさない
- エラーを処理するか、判断に必要な文脈を付けて呼び出し元へ返す
- 利用者向けメッセージと、開発者向けの原因情報を分ける
- 同じエラーを複数レイヤーで重複してログ出力しない
- 予想可能な失敗を `panic` や例外的なプロセス終了で処理しない
- 秘密情報、個人情報、認証情報をエラーやログへ含めない

## エラーの分類

| 分類 | 例 | 主な扱い |
| --- | --- | --- |
| Validation Error | サイズが範囲外、ブラウザが未選択 | 入力箇所の近くへ修正方法を表示する |
| Domain Error | 許可されない状態遷移 | Domainで表現し、Applicationで利用者向け結果へ変換する |
| Not Found | 指定ブラウザが存在しない | 対象と確認方法を表示する |
| Conflict | 既存設定との競合 | 競合内容と選択肢を表示する |
| Infrastructure Error | OSコマンド、ファイル、通信の失敗 | 技術詳細を保持しつつ、境界で意味のあるエラーへ変換する |
| Unexpected Error | 想定していない不具合 | 一般的なメッセージを表示し、調査用情報をログへ残す |

HTTPステータスやエラーコードを導入する場合は、この分類との対応を境界側で定義します。DomainがHTTPなどの通信方式へ依存しないようにします。

## レイヤーごとの責務

### Domain

- 不変条件やドメインルールに違反したことを表す
- UI文言、ログ出力、HTTPステータス、OS固有情報を持たない
- 呼び出し側で分岐が必要なエラーは、型または判定可能な値として表現する

### Application

- DomainとInfrastructureのエラーを、ユースケース上の結果へ整理する
- 再試行、代替処理、処理中断などの方針を決める
- 技術的な失敗を利用者へそのまま公開しない

### Infrastructure・Interface Adapter

- 外部ライブラリやOSから返されたエラーへ、操作と対象の文脈を付ける
- 外部固有のエラーを、内側で定義された意味へ変換する
- 終了コード、標準エラー出力、パスなど、調査に必要な原因情報を保持する
- 秘密情報を含む可能性がある出力を、そのままログへ記録しない

### UI

- エラーを、入力項目、画面全体、一時通知など適切な位置へ表示する
- 利用者が修正可能な問題では、原因と次の行動を伝える
- 想定外のエラーでは内部情報を表示せず、再試行や問い合わせ方法を案内する
- エラー発生後も、安全に再操作または画面遷移できる状態を保つ

## Goのエラー

- エラーをラップする場合は `%w` を使用し、原因を追跡できるようにする
- 文脈には、失敗した操作と対象を含める
- エラー文字列は小文字で始め、末尾に句点を付けないというGoの慣習に従う
- 呼び出し側で判定する場合は、エラー文字列の比較を使用しない
- Sentinel Errorは、安定した分類として複数箇所から判定する必要がある場合に限定する
- 追加情報が必要な場合は、独自のエラー型を検討する

例:

```go
if err := launcher.Launch(ctx, browser); err != nil {
	return fmt.Errorf("launch browser %q: %w", browser.Name(), err)
}
```

対象に秘密情報や個人情報が含まれる場合は、エラーメッセージへ埋め込みません。

## ユーザー向けメッセージ

メッセージには、可能な範囲で次を含めます。

1. 何ができなかったか
2. 利用者が確認または修正できること
3. 必要な場合は再試行や問い合わせ方法

```text
ブラウザを起動できませんでした。ブラウザがインストールされているか確認して、もう一度お試しください。
```

避ける表現:

- 「エラーが発生しました」だけで終わる
- スタックトレースやOSコマンドをそのまま表示する
- 利用者に原因がない問題で、入力や操作を責める
- 実際には保証できない復旧方法を案内する

## ログレベル

| レベル | 用途 | 例 |
| --- | --- | --- |
| Debug | 開発時の詳細な調査情報 | 選択された処理経路、外部処理の所要時間 |
| Info | 正常な重要イベント | アプリ起動、設定変更、ブラウザ起動完了 |
| Warn | 処理を継続できる想定外の状態 | 設定値の代替値使用、再試行 |
| Error | 処理を完了できず、調査が必要な失敗 | ブラウザ起動失敗、設定保存失敗 |

- 正常な入力エラーをすべてErrorとして記録しない
- 同じ失敗を各レイヤーで繰り返し記録しない
- 高頻度処理のログ量と性能への影響を考慮する
- Debugログを本番相当環境で常時有効にしない

## ログへ含める情報

- 発生した操作
- 対象を識別する安全な情報
- エラー分類またはコード
- 原因を追跡するための相関ID（導入した場合）
- 再試行回数や所要時間など、調査に必要な値

## ログへ含めない情報

- APIキー、アクセストークン、パスワード
- Cookie、認証ヘッダー、セッション情報
- 不要な個人情報
- ユーザーのホームディレクトリなど、不要な完全パス
- 外部コマンドの出力全文（安全性を確認して必要部分だけ記録する）

## 再試行

- 一時的な失敗であり、同じ操作を繰り返しても安全な場合だけ自動再試行する
- 回数と待機時間に上限を設ける
- 入力不正や権限不足など、再試行で改善しないエラーを繰り返さない
- ブラウザの多重起動など、副作用が重複しないことを確認する
- 最終的に失敗した場合は、試行回数を原因情報へ含める

## エラー処理のチェックリスト

- [ ] エラーを処理する責務が適切なレイヤーにある
- [ ] 呼び出し元が必要なエラー分類を判定できる
- [ ] 元の原因を追跡できる
- [ ] 利用者向けメッセージから次の行動が分かる
- [ ] 内部情報や秘密情報を利用者へ公開していない
- [ ] 同じエラーを重複してログ出力していない
- [ ] エラー経路をテストしている
- [ ] 再試行による副作用の重複がない

## 導入時に決める事項

- エラーコードの体系とGo・React間の伝達形式
- 使用するロガーと構造化ログのフィールド
- ログの保存場所、保持期間、ローテーション
- 利用者がログを確認・提供する方法
- 想定外エラーの通知または収集方法
