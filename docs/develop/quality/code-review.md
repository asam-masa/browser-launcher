# コードレビュー観点

## 目的

コードレビューでは、欠陥の発見だけでなく、設計判断の妥当性を確認し、プロジェクト内で知識を共有します。好みではなく、要件・設計原則・具体的なリスクを根拠にコメントします。

PRの運用とコメント方法は、[PR・レビュー運用](../workflow/pull-request-review.md)を参照してください。

## 確認する順序

細部から読み始めず、次の順序で確認します。

1. チケットの目的と完了条件を満たしているか
2. 変更方針と責務の分け方が妥当か
3. 正しく安全に動作するか
4. テストで重要な振る舞いを保護できているか
5. 命名や記述が読みやすいか

## レビュー観点

### 要件・正しさ

- チケットやPRに記載された要件を満たしているか
- 正常系だけでなく、境界値・異常系・部分的な失敗が考慮されているか
- 既存機能への意図しない影響がないか
- エラーを握りつぶさず、呼び出し側が適切に扱えるか

### 設計・責務

- 変更理由が説明され、より単純な設計で解決できないか検討されているか
- 責務が明確で、適切なレイヤーに配置されているか
- ドメインルールがUI、フレームワーク、永続化の都合に依存していないか
- 依存関係が内側のレイヤーへ向いているか
- 将来を予測した過度な抽象化や、用途のないインターフェースがないか

### Go

- 標準ライブラリとGoの慣用的な書き方を優先しているか
- エラーに呼び出し元が判断できる文脈が付いているか
- `context.Context` が必要な境界で適切に伝播されているか
- goroutine、ファイル、接続などのリソースが確実に終了・解放されるか
- コメントはコードの言い換えではなく、公開APIや判断理由を説明しているか

### React・フロントエンド

- コンポーネントの責務と状態の所有場所が明確か
- 不要な再レンダーや副作用を生む実装になっていないか
- ローディング、データなし、エラー時の表示が考慮されているか
- キーボード操作、ラベル、フォーカスなど基本的なアクセシビリティを満たすか
- ユーザー向けメッセージが、原因と次の行動を理解できる表現になっているか

### テスト

- 変更した振る舞いに対するテストが追加・更新されているか
- 実装の内部構造ではなく、外部から観測できる振る舞いを検証しているか
- 正常系、主要な異常系、重要な境界値が含まれているか
- テストが独立しており、実行順序や外部環境へ不必要に依存していないか
- テストを追加しない場合、その理由と代替の確認方法が妥当か

### セキュリティ・運用

- 入力値の検証と出力時のエスケープが適切か
- 秘密情報や個人情報をコード、ログ、エラーメッセージへ含めていないか
- ファイルパス、URL、OSコマンドなど外部入力を安全に扱っているか
- 権限を必要最小限にし、危険な操作に確認や制限があるか
- 障害調査に必要な情報を残しつつ、ログが過不足なく設計されているか

### 可読性・保守性

- 名前から責務や意図が分かるか
- 重複や複雑な分岐を、挙動を変えずに単純化できないか
- 変更に伴ってドキュメントや設定も更新されているか
- 新しい外部ライブラリの必要性、保守状況、ライセンスが説明されているか

## レビューの完了条件

- 必須対応のコメントがすべて解決されている
- 未解決の質問に合意または回答がある
- 必須のビルド、テスト、静的解析が成功している
- レビュアーが承認後の追加差分を確認している
