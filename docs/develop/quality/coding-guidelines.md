# コーディングガイドライン

## 目的

コードの書き方に関する判断基準を共有し、読み手が実装意図を理解しやすい状態を保ちます。FormatterやLinterで自動化できる規則はツールへ任せ、文書では設計と可読性に関わる方針を扱います。

## 共通方針

- 正しさを保てる最も単純な実装を選ぶ
- 名前は実装方法ではなく、役割やドメイン上の意味を表す
- 一つの関数、型、コンポーネントには明確な責務を持たせる
- 早すぎる共通化を避け、重複の背景と変更理由が同じ場合に抽象化する
- 暗黙の規約より、型と小さな関数で制約を表現する
- コメントはコードの言い換えではなく、理由、制約、非自明な判断を書く
- 未使用コード、コメントアウトしたコード、一時的なデバッグ処理を残さない
- ツールが生成したファイルは、生成元と更新方法を明確にする

## 命名

- プロジェクト内で同じ概念には同じ用語を使う
- 略語は、一般的で誤解がないものに限定する
- `data`、`info`、`manager`、`util` のように責務が曖昧な名前を安易に使わない
- 真偽値には、状態や条件が読み取れる名前を付ける
- 単位を持つ数値には、必要に応じて名前へ単位を含める
- コレクションには、要素が複数であることが分かる名前を使う

## コメント・ドキュメント

- 公開APIには、利用者が責務、前提、重要な副作用を理解できる説明を書く
- 「何をしているか」がコードから明らかな場合はコメントを追加しない
- 回避策や一見不自然な実装には、理由と解除条件を記載する
- TODOには、可能であれば関連チケットを付ける
- コード変更によって説明が古くなった場合は、同じ変更で更新または削除する

## Go

### 基本

- `gofmt` で整形する
- 標準ライブラリとGoの慣用的な書き方を優先する
- パッケージ名は短い小文字とし、そのパッケージが提供する概念を表す
- パッケージ名を繰り返す名前を避ける
- `init` とグローバルな可変状態は、明確な必要性がない限り使用しない
- `panic` は通常のエラー処理に使用しない

### 関数・型

- ゼロ値を安全に使用できる設計を検討する
- 引数が多い場合は、責務の分割または意味のある入力型を検討する
- Boolean引数で呼び出しの意味が分かりにくくなる場合は、別の型や関数にする
- ポインタは、状態変更、コピーコスト、`nil` の意味が必要な場合に使用する
- GetterやSetterを機械的に作らず、不変条件を守る操作としてメソッドを設計する
- インターフェースは利用側で、小さく定義する

### エラー

- エラーを無視しない
- エラーへ処理内容や対象を判断できる文脈を付ける
- 判定が必要なエラーは `errors.Is` または `errors.As` で扱えるようにする
- 同じエラーを複数レイヤーで重複してログ出力しない
- 詳細は[エラー・ログ方針](../architecture/error-handling.md)に従う

### Context・並行処理

- `context.Context` は第一引数として受け取り、構造体へ保存しない
- キャンセル、期限、リクエストスコープの値を下位処理へ伝播する
- 任意の引数を渡す目的でContextを使用しない
- goroutineを開始した場所で、終了条件とエラーの扱いを説明できるようにする
- チャネルは所有者とcloseする責任を明確にする
- 共有状態より、所有権の移動やメッセージ受け渡しを検討する

## React・TypeScript

### コンポーネント

- コンポーネントは、表示と操作の一つの責務へ絞る
- 再利用の可能性だけを理由に、早期に汎用コンポーネント化しない
- Propsは必要最小限にし、意味のない大量の真偽値を避ける
- 派生可能な値を重複してstateに保持しない
- 状態は、それを必要とする最も近い共通の所有者に置く
- リスト要素のkeyに、不安定な配列インデックスを安易に使用しない

### Hooks・副作用

- HooksはコンポーネントまたはCustom Hookのトップレベルで呼び出す
- `useEffect` は外部システムとの同期に使用し、単純な値計算には使用しない
- Effectの依存値を意図的に省略しない
- タイマー、購読、イベントリスナーなどはcleanupする
- 複数コンポーネントで共有する状態を持つ処理はCustom Hookを検討する

### TypeScript

- `any` を原則として使用せず、境界の不明な値は `unknown` として検証する
- APIやIPCから受け取る値は、型注釈だけで安全とみなさず実行時に検証する
- 型アサーションは、値の安全性を確認できる場合に限定する
- Domain上取り得ない状態を表現しにくい型設計を検討する
- Enum、Union、定数オブジェクトは、用途と生成コードとの互換性を考えて選ぶ

### UI・アクセシビリティ

- セマンティックなHTML要素を優先する
- 操作要素にはラベルとキーボード操作手段を提供する
- 色だけで状態やエラーを伝えない
- 非同期処理では、実行中、成功、失敗の状態を利用者へ伝える
- ユーザー向けエラーは[エラー・ログ方針](../architecture/error-handling.md)に従う

## 外部ライブラリ

導入前に、次を確認してPRへ記載します。

- 解決する課題と、標準機能や既存依存で解決できない理由
- メンテナンス状況と利用実績
- ライセンス
- セキュリティ上の既知の問題
- バンドルサイズや実行時コスト
- ライブラリへの依存を境界へ隔離できるか

## 自動化する項目

利用するツールが確定した段階で、少なくとも次をローカルとCIで自動化します。

- Goおよびフロントエンドのフォーマット
- 静的解析と型チェック
- Unit Test
- 未使用コードや不正な依存関係の検出

具体的なコマンドと設定ファイルは、導入後に本ドキュメントへ追記します。
