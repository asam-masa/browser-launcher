# テスト方針

## 目的

テストは、重要な振る舞いを保護し、設計改善や機能追加を安全に行うために作成します。テスト数やカバレッジ率そのものを目的にはしません。

## 基本原則

- 実装の内部構造ではなく、外部から観測できる振る舞いを検証する
- 高速で安定したUnit Testを中心にし、境界のリスクをIntegration Testで補う
- E2E Testは、主要なユーザー操作に限定する
- 正常系だけでなく、重要な異常系と境界値を検証する
- 不具合修正では、可能な限り修正前に失敗する再現テストを追加する
- テストしにくいコードは、責務や依存関係を見直すきっかけとして扱う
- 時刻、乱数、OS、外部通信など不安定な依存を制御する

## テストの種類

| 種類 | 対象 | 実行タイミング |
| --- | --- | --- |
| Unit Test | Domain、Application、関数、Hooksなどの小さな単位 | ローカルおよびすべてのPR |
| Integration Test | OS・ファイル・通信・永続化などとの境界 | PRまたは対象変更時 |
| E2E Test | UIから主要機能までの利用者視点のフロー | PR、リリース前、または定期実行 |
| Manual Test | 自動化が難しいOS・画面上の振る舞い | 対象変更時 |

## レイヤー別の方針

### Domain

- 不変条件、状態遷移、値オブジェクトの生成条件をUnit Testで検証する
- 外部依存を持ち込まず、高速に実行できる状態を保つ
- 正常値、境界値、無効値をテーブル駆動テストで表現することを検討する

### Application

- ユースケースの入力、結果、外部依存への指示を検証する
- 成功、対象なし、入力不正、外部処理失敗など主要な分岐を扱う
- テストダブルは、ユースケースが依存する最小限のインターフェースに対して使用する
- 呼び出し回数など実装詳細の検証は、振る舞い上必要な場合に限定する

### Infrastructure・境界

- OSコマンドの引数、パス、外部形式との変換をIntegration Testで検証する
- 一時ディレクトリや隔離されたテストデータを使用する
- 開発者のブラウザ設定や実ファイルを変更しない
- OS固有テストには対象OSが分かる名前やビルド条件を付ける
- 実行環境が限られるテストは、実行条件と代替確認方法を記載する

### React・UI

- ユーザーが見る表示と操作結果を検証する
- ローディング、データなし、入力エラー、処理失敗の状態を扱う
- 実装上のstateや内部メソッドを直接検証しない
- DOM構造やスナップショットだけに依存せず、roleやlabelなど利用者視点で要素を取得する
- 主要フローは、必要に応じてGoとの境界を含むE2E Testで保護する

## Goのテスト

- 標準の `testing` パッケージを基本とする
- 複数ケースを同じ振る舞いとして表現できる場合は、テーブル駆動テストを使用する
- サブテストには、失敗内容を理解できる名前を付ける
- 並列実行は、共有状態がなく安全であることを確認してから使用する
- ヘルパー関数では `t.Helper()` を使用する
- エラー文字列全体ではなく、`errors.Is` や `errors.As` で意味を検証する

外部テストライブラリは、標準機能では読みやすさや保守性を十分に確保できない場合に限り、採用理由を説明して導入します。

## テストダブル

- 実際の振る舞いを軽量かつ安全に確認できる場合は、実装に近いFakeを優先する
- Mockは、外部への指示や失敗条件を制御する必要がある場合に使用する
- 外部ライブラリの型を直接Mockせず、プロジェクトが必要とする契約を境界に置く
- Mockの期待値が増えすぎる場合は、テスト対象の責務が大きすぎないか確認する

## カバレッジ

- 一律の数値目標を完了条件にしない
- 未テストの重要な分岐やドメインルールを発見する補助指標として使用する
- 単純なデータ構造や生成コードを埋めるためだけのテストを作らない
- カバレッジが下がる変更では、重要な振る舞いが未保護になっていないか確認する

## テストを追加しない場合

次のような場合は自動テストを追加しない判断があり得ます。

- 文言やドキュメントだけの変更
- 自動化コストが効果に対して著しく高い一時的な検証
- 現在の環境では再現できないOS固有の振る舞い

その場合は、理由、実施した手動確認、残るリスクをPRへ記載します。

## PR前の確認

- [ ] 変更した振る舞いに対応するテストがある
- [ ] 主要な正常系・異常系・境界値を検証している
- [ ] テストが実行順序や開発者環境へ依存していない
- [ ] 失敗時に原因を理解できるテスト名とメッセージになっている
- [ ] 必要なUnit Test、Integration Test、E2E Testを実行した
- [ ] 手動確認と未実施の確認をPRへ記載した

## CI

GitHub Actionsの`.github/workflows/ci.yml`で、`pull_request`と`main`への`push`を契機に検証します。CIは回帰検出とコンパイル確認を担当し、実機固有の振る舞いを代替しません。

| 環境 | 自動検証 |
| --- | --- |
| Linux | Markdown Lint、ローカルリンク検査、ReactのUnit Testとビルド、GoのUnit Test、race detector、`go vet` |
| Windows | ReactのUnit Testとビルド、GoのUnit Test、`go vet`、`go build ./...` |

CIでは、GitHub-hosted runnerを使用します。workflowの`GITHUB_TOKEN`は`contents: read`だけを許可し、Secrets、デプロイ、コード署名を使用しません。生成した実行ファイルはartifactやGitHub Releasesへ保存しません。

GitHub公式Actionは、確認済みリリースのコミットSHAへ固定します。更新時は公式リポジトリのリリースとSHAを確認し、LinuxとWindowsのジョブが成功することを検証します。

依存関係のキャッシュには、`actions/setup-go`と`actions/setup-node`の標準機能を使用します。依存関係の再現には、`go.sum`、ルートの`package-lock.json`、`frontend/package-lock.json`を使用します。

`frontend/wailsjs`はGitで管理しないため、クリーンなrunnerではFrontendのテストとビルドの前にWails v2.12.0でバインディングを生成します。Windowsでは`scripts/develop/generate-wails-bindings.ps1`を使用し、Linuxでは同じWails CLIの`generate module`を実行します。

次の項目はWindows実機で確認します。

- Chromeの起動、ウィンドウ追跡、位置とサイズ
- プロファイル選択画面から通常ウィンドウへ遷移する操作
- 取消、タイムアウト、起動失敗後の再実行
- 複数ディスプレイ、画面の向き、DPIが異なる環境
- Wailsの開発モードと生成したWindows実行ファイルの起動

CIはバイナリを配布しないため、インストール、アンインストール、コード署名、Microsoft Defender SmartScreenを検証しません。

## 導入時に決める事項

- E2E Testのツールと対象ブラウザ・OS
- テストデータ、Fixture、Golden Fileの配置規則
- 時間のかかるテストを分類する方法

## Reactのテスト基盤

ReactのUnit Testとコンポーネントテストには、次のツールを使用します。

| ツール | 役割 |
| --- | --- |
| Vitest | Viteの設定とTypeScriptを利用するテストランナー |
| Testing Library | 利用者が確認できる表示と操作を基準にしたコンポーネントテスト |
| user-event | キーボードやポインターによる操作の再現 |
| jsdom | Unit Testで使用するDOM環境 |

Viteの設定とTypeScriptを共有できるため、Vitestを採用します。Reactコンポーネントは、内部のstateやDOM構造ではなく、role、label、表示結果を基準にTesting Libraryで検証します。ブラウザ固有の表示やWailsとの実通信はjsdomで再現できないため、Manual Testまたは今後導入するE2E Testで確認します。

`frontend`ディレクトリで、次のコマンドを実行します。

```bash
npm test
```
