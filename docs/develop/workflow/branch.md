# ブランチ戦略

## 方針

GitHub Flowを採用します。長期間維持する開発ブランチは作らず、`main` と短命な作業ブランチで運用します。

## 基本ルール

- `main` は常にビルド・テスト可能で、リリースできる状態を保つ
- 作業ブランチは最新の `main` から作成する
- 一つのブランチでは一つの関心事を扱う
- `main` への変更は原則としてPRを経由する
- レビューと必須の検証が完了してからマージする
- マージ後、不要になった作業ブランチは削除する
- 作業ブランチへの強制プッシュは、レビュー中の履歴を失うため原則として避ける

緊急修正で手順を省略した場合は、理由と実施した確認を記録します。

## ブランチ名

次の形式を推奨します。

```text
<type>/<ticket-id>-<short-description>
```

`type` はチケットタイプと対応させます。

| type | 用途 | 例 |
| --- | --- | --- |
| `feature` | 機能追加 | `feature/BL-123-browser-size` |
| `fix` | 不具合修正 | `fix/BL-124-window-position` |
| `refactor` | 外部仕様を変えない改善 | `refactor/BL-125-launcher-service` |
| `docs` | ドキュメントのみの変更 | `docs/BL-126-review-guide` |
| `chore` | 開発環境や保守作業 | `chore/BL-127-update-tooling` |

- 説明部分は小文字の英数字とハイフンを使用する
- チケットがない軽微な作業では、チケットIDを省略してよい
- 個人名は付けず、変更内容が推測できる名前にする

## マージ方法

原則として Squash and merge を使用し、PRを一つの論理的な変更として `main` に残します。複数コミットの履歴自体に意味がある場合のみ、理由をPRに記載して別の方法を選択します。
