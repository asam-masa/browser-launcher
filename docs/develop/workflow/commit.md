# コミット

## 目的

コミットは、変更の意図を後から追跡でき、安全にレビューや切り戻しができる単位にします。

## コミットの粒度

- 一つのコミットでは一つの論理的な変更を扱う
- リファクタリングと振る舞いの変更は、可能な限り分ける
- コードと、その変更に必要なテスト・ドキュメントは同じコミットに含めてよい
- ビルドできない、またはテストが失敗する中間状態を共有ブランチへ残さない
- フォーマットだけの変更を機能変更へ混在させない

## コミットメッセージ

次の形式で、一行に簡潔に記述します。

```text
<ticket-id> <変更内容を表す日本語>
```

例:

```text
BL-123 ブラウザ起動時にウィンドウサイズを指定できるようにする
#45 無効な画面位置を指定した際のエラーを修正する
```

- Jiraを使う場合はチケットID、GitHub Issueを使う場合は `#<番号>` を先頭に付ける
- チケットがない軽微な変更ではIDを省略してよい
- 「修正」「対応」のような曖昧な表現だけで終わらせず、何が変わるかを書く
- 現在形で、変更後の状態が分かるように書く

## ステージング

- `git status` と `git diff` で対象を確認してからコミットする
- `git add` ではファイルまたは差分を明示的に選ぶ
- 意図しないファイルの混入を防ぐため、原則として `git add .` を使用しない
- 秘密情報、個人用設定、デバッグ用ファイルを含めない

## コミットメール

個人メールをGit履歴へ記録しないため、GitHubが提供するID付き`noreply`メールを使用します。リポジトリ単位の設定を優先し、他のリポジトリへ影響するグローバル設定は必要な場合だけ変更します。

```bash
git config user.email "<GitHubが提供するID付きnoreplyメール>"
```

設定値はGitHubの「Settings」から「Emails」で確認します。メールアドレスの値を、文書、チケット、Pull Request、レビュー、ログへ記録しません。設定変更は今後のコミットだけに適用され、過去のコミットは変更しません。
