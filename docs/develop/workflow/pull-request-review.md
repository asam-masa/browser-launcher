# PR・レビュー運用

## 目的

PRは、一つの変更について目的、実装方針、検証結果を共有し、安全に `main` へ統合するために使用します。

## PRの基本ルール

- 一つのPRでは一つの関心事を扱う
- ドラフトPRを使い、設計や実装途中でも早めに方向性を共有する
- レビュー依頼時点で、原則としてビルド・テスト可能な状態にする
- 変更理由、主な設計判断、確認方法をPR本文に記載する
- レビューに不要な整形、リネーム、生成物を混在させない
- 関連するチケットをリンクする

## PR本文に記載する項目

PR本文には次の項目を設けます。該当する内容がない場合も項目を削除せず、`なし` または未実施の理由を記載します。

| 項目 | 記載内容 |
| --- | --- |
| `Overview` | 変更の背景、目的、変更概要 |
| `Related` | 関連するJira、GitHub Issue、PR、設計資料 |
| `AI Review` | AIレビューの実施有無、使用ツール、主な指摘と対応結果 |
| `Result` | テスト、静的解析、ビルド、手動確認の結果 |
| `Remarks` | レビューしてほしい点、対象外、制約、後続作業、規模超過の理由 |

PR作成時は、[PRテンプレート](../../../.github/pull_request_template.md)を使用します。

```markdown
# Pull Request

## Overview

<!-- 変更の背景、目的、変更概要を記載してください -->

## Related

<!-- 関連するJira、GitHub Issue、PR、設計資料を記載してください。ない場合は「なし」と記載してください -->

## AI Review

<!-- AIレビューの実施有無、使用したツール、主な指摘と対応結果を記載してください。未実施の場合は理由を記載してください -->

## Result

<!-- 実行したテスト、静的解析、ビルド、手動確認と結果を記載してください。未実施の項目には理由を記載してください -->

- [ ] テスト
- [ ] 静的解析
- [ ] ビルド
- [ ] 手動確認

## Remarks

<!-- 重点的にレビューしてほしい点、対象外、既知の制約、後続作業、PR規模超過の理由を記載してください -->
```

画面表示を変更した場合はスクリーンショットまたは動画を、再現しにくい不具合を修正した場合は再現手順と修正後の結果を添えます。

### AI Reviewの記載方法

- AIレビューを実施した場合は、使用したツールまたはモデル、確認観点、主な指摘を記載する
- レビュー指摘には`must`、`want`、`ask`、`imo`、`nits`、`info`のプレフィックスを残す
- 各指摘に、対応状況と修正内容、回答、または対応しない理由を記載する
- `must`または`want`を修正しない場合は、理由を必ず記載する
- 未解決の`must`がある場合は通常PRを作成せず、必要に応じてDraft PRで共有する
- 未回答の`ask`または対応方針が未合意の`want`がある場合はDraft PRとして扱う
- AIがコードや文書を生成しただけの場合は、レビューを実施したことにはしない
- AIレビューを実施していない場合は、`未実施` と理由を記載する
- AIレビューは人間によるセルフレビューやコードレビューの代替にしない

指摘がある場合は、次の形式を使用します。

```markdown
### review-code-changes

| Prefix | Finding | Status | Response |
| --- | --- | --- | --- |
| must | 入力値の検証が不足している | 修正済み | Controllerで検証し、異常系テストを追加 |
| want | 重複した変換処理がある | 未修正 | 後続チケットで扱う理由と合意内容を記載 |
```

指摘がない場合は`指摘なし`と記載します。レビューを実施していない場合は`未実施`と理由を記載します。

### Resultの記載方法

- コマンドを実行した場合は、可能な範囲でコマンドと結果を記載する
- 手動確認では、確認した操作、環境、結果を記載する
- 対象外の項目は未チェックのままにせず、`対象外` と理由を記載する
- 失敗している検証や未実施の検証を隠さず、残るリスクを記載する

## PRの規模

次の数値は機械的な合否ではなく、分割を検討するきっかけとして使用します。

| 指標 | 推奨 | 分割を強く検討 |
| --- | ---: | ---: |
| 変更行数（追加 + 削除） | 200行以内 | 400行超 |
| 変更ファイル数 | 10ファイル以内 | 20ファイル超 |

変更行数とファイル数は、自動生成ファイル、ロックファイル、スナップショットなどを除いた、実質的なレビュー対象で数えます。

大規模なリネームなど、一つの関心事として分割するとかえって理解しにくい変更は、基準を超えても構いません。その理由とレビュー方法を `Remarks` に記載します。

### 小さく保つ利点

- レビューの負荷が下がり、欠陥と設計上の問題を見つけやすい
- 変更意図が明確になり、履歴を追いやすい
- 不具合発生時の切り戻しと原因特定を局所化できる
- フィードバックを早く得られる

## 大きな変更の分割

機能フラグや後方互換性を利用し、可能であれば各PRを直接 `main` へ安全にマージできる単位に分けます。例えば、次の順で分割します。

1. 振る舞いを保護するテスト
2. 基盤や内部APIの追加
3. 新しい振る舞いの実装
4. 呼び出し元の切り替え
5. 古い実装の削除

各PRを単独で `main` へ入れられない場合のみ、短命な統合作業ブランチを使用します。

1. `main` から統合作業ブランチを作成する
2. 統合作業ブランチから関心事ごとの作業ブランチを作成する
3. 各作業ブランチから統合作業ブランチへPRを作成する
4. 依存関係の下位（基盤・共通）から順にレビュー・マージする
5. すべて揃ったら統合作業ブランチから `main` へ最終PRを作成する

最終PRにはレビュー済みのPRを列挙し、追加差分の有無と統合後の検証結果を記載します。統合作業ブランチを長期間残さないようにします。

## レビューコメントのプレフィックス

修正の必要性を明確にするため、レビューコメントには次のプレフィックスを付けます。

| プレフィックス | 対応 | 意味 |
| --- | --- | --- |
| `must:` | 必須 | 正しさ、セキュリティ、要件、重大な保守性の問題。マージ前に解決する |
| `want:` | 原則必須 | 品質向上のため、このPRでの修正を求める。対応しない場合は合意が必要 |
| `ask:` | 回答 | 意図や仕様を確認する質問。回答によって修正が必要になる場合がある |
| `imo:` | 任意 | レビュアーの意見としての改善案 |
| `nits:` | 任意 | 表記などの軽微な指摘 |
| `info:` | 不要 | 今後に向けた補足や知識共有 |

`imho` は `imo` との違いが曖昧になりやすいため使用しません。

コメントではプレフィックスだけでなく、問題、その影響、可能であれば改善案を記載します。

```text
must: 外部入力がそのままファイルパスに使われているため、意図しないファイルを参照できます。
許可するディレクトリを限定し、正規化後のパスを検証してください。
```

## レビューの進め方

### 作成者

- すべての `must:` と `want:` に対応または返信する
- `ask:` に回答する
- 修正したコメントには、変更箇所や判断を返信する
- 指摘へ対応しない場合は理由を説明し、レビュアーと合意する
- レビュー後に大きな変更を加えた場合は、再レビューを依頼する

### レビュアー

- [コードレビュー観点](../quality/code-review.md)に沿って確認する
- 人ではなくコードと影響を対象に、根拠を添えてコメントする
- 好みだけの提案は必須対応にしない
- 指摘への対応後、会話を解決する前に差分を確認する
- 自分で確認していない内容を推測だけで承認しない

## レビュー依頼前のセルフチェック

- [ ] PRの目的が一つの関心事に閉じている
- [ ] チケットの受け入れ条件を満たしている
- [ ] 自分で差分全体をレビューした
- [ ] テストを追加・更新し、必要な検証が成功している
- [ ] 不要なデバッグコード、コメントアウト、生成物が含まれていない
- [ ] セキュリティ上の影響を確認した
- [ ] ドキュメントと設定を必要に応じて更新した
- [ ] APM導入後に `.apm/` を編集した場合、`make apm-sync` の生成物も更新した
- [ ] PR本文がテンプレートに沿っている

## マージ後のローカル整理

PRのマージ後は、次の順でローカル環境を整理します。`$cleanup-after-merge` Skillを使用する場合も、同じ条件に従います。

1. GitHub上で対象PRがマージ済みであることを確認する
2. 未コミットと未追跡の変更がないことを確認する
3. 削除するローカル作業ブランチと影響を提示し、依頼者の承認を得る
4. `origin/main`を取得し、ローカル`main`をfast-forwardだけで更新する
5. 承認されたローカル作業ブランチだけを`git branch -d`で削除する
6. 現在のブランチ、`main`のコミット、作業ツリー、リモートブランチの有無を報告する

未マージのPR、変更が残る作業ツリー、fast-forwardできない`main`では処理を停止します。`git branch -D`、reset、force、未コミット変更の破棄または退避は行いません。リモートブランチは、依頼者から明示的な依頼がない限り削除しません。
