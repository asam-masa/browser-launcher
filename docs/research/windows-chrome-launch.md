# Windows 11におけるChromeの起動と配置

## 目的

Windows 11上でGoogle Chromeの新しいウィンドウを指定した位置とサイズへ起動できるかを検証し、MVPの実装方針を決めるための根拠を残します。

本調査は[プロダクト要件](../product/requirements.md)の未決定事項を対象とします。製品コードの実装は対象外です。

## 明らかにしたい問い

1. ユーザー単位またはシステム単位でインストールされたChromeを検出できるか
2. Chromeの未起動時と起動済み時の両方で、新しいウィンドウを1つ開けるか
3. 起動時に指定した位置とサイズがどのように反映されるか
4. Windowsの表示倍率によって要求値と実測値がどう変化するか
5. プロファイル選択後に開いたChromeウィンドウを識別し、実際の位置とサイズを確認できるか

## 一次情報から確認した事実

### Chromeの起動オプション

Chromiumのソースコードには、初期位置を指定する`window-position=x,y`と初期サイズを指定する`window-size=w,h`が定義されています。

ただし、この定義だけではChrome起動済み時の挙動、指定値の保証、将来の互換性までは確認できません。実機検証の結果と組み合わせて判断します。

### Chromeの検出

Windowsは、実行ファイル名から完全なパスを解決する登録先として`App Paths`を提供しています。ユーザー単位は`HKEY_CURRENT_USER`、システム単位は`HKEY_LOCAL_MACHINE`が対象です。

検証スクリプトでは次の順で候補を確認します。

1. ユーザー単位の`App Paths`
2. システム単位の`App Paths`（64ビットと32ビットのレジストリビュー）
3. ユーザー単位の標準インストール先
4. システム単位の標準インストール先

ADR-0001では、この探索順序を採用しました。現在の実機ではシステム単位の64ビット`App Paths`からの検出を確認済みです。ユーザー単位、32ビットビュー、フォールバック先からの検出は未検証として残します。

`App Paths`の登録名だけでは実行ファイルの同一性を保証できないため、レジストリから取得したパスは正規化し、上記の標準インストール先のいずれかと一致する場合だけ採用します。製品実装では、Google Chromeのデジタル署名を信頼判定へ含めるかを別途決定します。

### ウィンドウの位置とサイズ

Windowsの`GetWindowRect`は、トップレベルウィンドウの外接矩形をスクリーン座標で取得します。一方で、次の制約があります。

- 呼び出し元のDPI認識状態に応じて値が仮想化される
- Windows Vista以降では不可視のリサイズ境界を含む場合がある
- 表示上の境界は`DwmGetWindowAttribute`の`DWMWA_EXTENDED_FRAME_BOUNDS`で別に取得できるが、その値はDPI調整されない

したがって、要求値との比較ではDPI、外接矩形、表示上の境界を区別します。

## 検証方法

### 検証スクリプト

[`verify-chrome-launch.ps1`](../../scripts/spike/verify-chrome-launch.ps1)をWindows PowerShell 5.1以降で使用します。

スクリプトは既定ではChromeの検出だけを行います。`-Launch`を指定した場合だけ、次を実行します。

1. 起動前のChromeトップレベルウィンドウを記録する
2. `new-window`、`window-position`、`window-size`を指定してChromeを起動する
3. 起動後に追加されたChromeトップレベルウィンドウを待機する
4. 指定された場合は、プロファイル選択中に候補ウィンドウが置き換わるかを待機する
   - 遷移中に出現した候補を記録する
   - 待機終了時点で存在する候補を再列挙する
   - 補正対象となる置き換わり候補が一意でなければ失敗させる
   - 測定と補正の直前に、ウィンドウハンドル、PID、プロセス開始時刻、ウィンドウクラスを再確認する
5. 位置とサイズが連続して同じ値になるまで待機する
6. `ApplyPosition`が指定された場合は、次の二段階で`SetWindowPos`による補正を行う
   1. `SWP_NOSIZE`を指定し、サイズを変えずプライマリディスプレイへ移動する
   2. 対象ウィンドウが現在のプライマリモニター上にあり、DPIと位置が安定したことを確認する
   3. 移動後のウィンドウから取得したDPIで論理ピクセルを物理座標へ変換し、最終位置とサイズを適用する
7. 起動前のウィンドウ数、候補の種別、置き換わりの有無、移動前、移動後、最終補正後の`GetWindowRect`、DWMの表示境界、ウィンドウのDPIをJSONで出力する
8. 最終外接矩形のX、Y、幅、高さが要求した物理矩形と完全一致することを確認し、不一致の場合は配置失敗として出力する

絶対パス、ウィンドウタイトル、閲覧内容は出力しません。

`Chrome_WidgetWin_1`クラスだけでは、通常のブラウザウィンドウとプロファイル選択画面を安全に区別できません。スクリプトは検出したウィンドウを`UnverifiedChromeTopLevelWindow`として出力し、通常のブラウザウィンドウであることを断定しません。

### 実行例

Windows PowerShellでリポジトリのルートへ移動し、検出だけを行います。

```powershell
.\scripts\spike\verify-chrome-launch.ps1
```

Chromeを指定位置へ起動して結果を取得します。

```powershell
.\scripts\spike\verify-chrome-launch.ps1 -Launch -X 100 -Y 100 -Width 1000 -Height 700
```

プロファイル選択画面が表示される環境では、待機時間内に利用者がプロファイルを選択し、候補ウィンドウの置き換わりを追跡します。

```powershell
.\scripts\spike\verify-chrome-launch.ps1 -Launch -ProfileSelectionWaitSeconds 15 -X 100 -Y 100 -Width 1000 -Height 700
```

置き換わりが検出されても、通常のブラウザウィンドウであることを機械的に保証するものではありません。実機検証では画面を目視し、測定対象と突き合わせます。

選択後の通常ウィンドウをプライマリディスプレイへ補正する場合は、`ApplyPosition`を指定します。この指定がない場合、スクリプトはウィンドウを移動・リサイズしません。

```powershell
.\scripts\spike\verify-chrome-launch.ps1 -Launch -ApplyPosition -ProfileSelectionWaitSeconds 15 -X 100 -Y 100 -Width 1000 -Height 700
```

補正ではPowerShellのスレッドをPer-Monitor DPI Aware V2として動作させ、プライマリディスプレイのDPIを基に論理ピクセルを物理座標へ変換します。最初の移動では`SWP_NOSIZE`を指定し、DPI変更の安定後に最終サイズを適用します。どちらの`SetWindowPos`にもアクティブ化とZオーダー変更を行わないフラグを指定します。

現在のプライマリモニターは`MonitorFromPoint`と`GetMonitorInfo`で取得します。セッション開始時のSystem DPIは使用せず、移動後の対象ウィンドウから`GetDpiForWindow`で取得したDPIを最終変換へ使用します。途中で失敗した場合は、自動で元の位置へ戻さず、処理段階、部分変更の有無、最後に取得できた矩形をJSONで出力します。安定待ちの途中で後続の測定に失敗した場合も、それ以前に最後に取得できた矩形を保持します。

WSLからWindows PowerShell 5.1を呼び出す場合は、`-File`へスクリプトのWindows UNCパスを渡します。実行ポリシーによってスクリプトを実行できない場合は、内容を確認したうえでPowerShellプロセスに限って`-ExecutionPolicy Bypass`を指定します。システムの実行ポリシーは変更しません。

### Go実装のIntegration Test

[`placement_windows_integration_test.go`](../../internal/infrastructure/chromewindowplacement/placement_windows_integration_test.go)は、製品実装の検出、起動、追跡、配置処理をWindows 11で検証します。テストは、起動前のスナップショットに存在しないChromeウィンドウを追跡し、識別情報を再検証してから二段階で配置します。第1段階後に取得したDPI、モニター領域、使用可能領域を用いて論理ピクセルの要求を再変換し、使用可能領域内であることを確認した場合だけ最終位置とサイズを適用します。

このテストはChromeを起動し、追跡したウィンドウを移動・リサイズします。`BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION`が`1`の場合だけ実行し、通常のテストではスキップします。配置に失敗しても元の位置へ戻さず、Chromeを自動終了しません。検証中に別のChromeウィンドウを開かないでください。

最終検証に失敗した場合、第1段階のモニター移動は完了している可能性があります。この場合は`StageFinalPlacement`、`PartiallyChanged=true`、最後に取得した矩形、入力項目ごとの問題を返し、最終的なリサイズは実行しません。実際の利用者向け文言への変換と表示は、起動操作をWailsとReactへ接続する後続作業で扱います。

Windows側からアクセスできるチェックアウトでは、Windows PowerShellで次を実行します。プロファイル選択画面が表示された場合は、60秒以内に既存ウィンドウがないプロファイルを選択します。

```powershell
$env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION = '1'
go test -run '^TestProviderPlaceIntegrationOnWindows$' -count=1 -v ./internal/infrastructure/chromewindowplacement
Remove-Item Env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION
```

異なるDPI間を検証する場合は、追跡完了後から配置開始までの準備時間を`0～60`秒で指定できます。待機中に、追跡した通常ウィンドウを移動元のディスプレイへ手動で移動します。表示倍率やWindows設定はテストから変更しません。

```powershell
$env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION = '1'
$env:BROWSER_LAUNCHER_WINDOW_PLACEMENT_PREPARE_SECONDS = '15'
go test -run '^TestProviderPlaceIntegrationOnWindows$' -count=1 -v ./internal/infrastructure/chromewindowplacement
Remove-Item Env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION
Remove-Item Env:BROWSER_LAUNCHER_WINDOW_PLACEMENT_PREPARE_SECONDS
```

使用可能領域を超える論理的な要求に対して、最終配置を実行しないことを確認する場合は、拒否テストモードを明示的に有効にします。テストは第1段階で対象ウィンドウをプライマリディスプレイへ移動しますが、最終的な位置とサイズは適用しません。

```powershell
$env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION = '1'
$env:BROWSER_LAUNCHER_WINDOW_PLACEMENT_REJECT_FINAL = '1'
go test -run '^TestProviderPlaceIntegrationOnWindows$' -count=1 -v ./internal/infrastructure/chromewindowplacement
Remove-Item Env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION
Remove-Item Env:BROWSER_LAUNCHER_WINDOW_PLACEMENT_REJECT_FINAL
```

今回の環境では、Windows版GoからWSLのUNCパスにある`go.mod`をロックできず、`go test`を直接実行できませんでした。WSL側でWindows amd64向けテスト実行ファイルを生成し、Windows PowerShellから実行しました。

```bash
GOCACHE=/tmp/browser-launcher-go-cache GOOS=windows GOARCH=amd64 \
  go test -c -o /tmp/chromewindowplacement.test.exe \
  ./internal/infrastructure/chromewindowplacement
```

Windows PowerShellから実行する場合は、`<distribution>`を使用中のWSLディストリビューション名へ置き換えます。

```powershell
$env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION = '1'
& "\\wsl.localhost\<distribution>\tmp\chromewindowplacement.test.exe" `
  '-test.run=^TestProviderPlaceIntegrationOnWindows$' '-test.v=true'
Remove-Item Env:BROWSER_LAUNCHER_RUN_WINDOW_PLACEMENT_INTEGRATION
```

### 検証履歴

最初の起動検証では、新しいChromeトップレベルウィンドウを識別できました。要求値と取得値は次のとおりです。

| 項目 | 要求値 | 外接矩形 | 表示境界 |
| --- | ---: | ---: | ---: |
| X | 100 | 708 | 715 |
| Y | 100 | 257 | 257 |
| 幅 | 1000 | 1144 | 1130 |
| 高さ | 700 | 877 | 870 |

取得したDPIは96でした。ただし、この実行では起動前のChromeウィンドウ数を結果へ出力しておらず、生成直後の位置とサイズが安定したことも確認していません。そのため、T-01またはT-02の確定結果としては扱いません。

実行時にはChromeのプロファイル選択画面が表示されました。目視確認により、測定対象は通常のブラウザウィンドウではなく、プロファイル選択画面だったことを確認しました。

Chromeの通常ウィンドウを起動した状態で再実行しても、新しい通常ウィンドウではなくプロファイル選択画面が表示されました。起動前には4個のChromeトップレベルウィンドウを検出し、追加された選択画面の測定値は安定していました。

この結果から、現在のChrome環境では`new-window`、`window-position`、`window-size`だけではプロファイル選択を越えて通常のブラウザウィンドウを直接起動できないことを確認しました。位置とサイズの起動オプションが通常ウィンドウへ反映されるかは、まだ検証できていません。

後続の検証では、起動前のウィンドウ数、候補ウィンドウの置き換わり、測定値の安定を記録し、プロファイル選択画面を測定した可能性、Chrome起動済み時に起動オプションが反映されない可能性、生成途中を測定した可能性を切り分けます。

プロファイル選択後の追跡検証では、選択画面の消失と別のChromeトップレベルウィンドウの出現を検出しました。目視確認により、置き換わった対象が通常のChromeブラウザウィンドウであることを確認しました。

| 項目 | 結果 |
| --- | --- |
| 起動前のChromeトップレベルウィンドウ数 | 2 |
| ウィンドウの置き換わり | 検出成功 |
| 測定値の安定 | 確認成功 |
| 対象ウィンドウのDPI | 144（150%相当） |
| 外接矩形 | X=-3686, Y=-718, W=2424, H=1400 |
| DWM表示境界 | X=-3600, Y=-713, W=3618, H=2091 |

負の座標から、対象ウィンドウはプライマリディスプレイ以外に配置された可能性が高いと判断します。また、外接矩形とDWM表示境界の寸法比は約1.5であり、DPI仮想化の影響と整合します。

この結果により、プロファイル選択後の通常ウィンドウを追跡できることは確認できました。一方で、異なるDPI座標系の値をそのまま比較できず、起動引数だけではプライマリディスプレイ上の要求位置へ配置されなかったため、DPI認識状態をそろえたWin32 APIによる確認・補正の検証が必要です。

最初の補正検証では、プロファイル選択後に通常のブラウザウィンドウが表示されたものの、測定前に候補のウィンドウハンドルが無効になり、`GetWindowRect`が失敗しました。`SetWindowPos`は呼び出されておらず、補正は未実施です。遷移途中の一時的なウィンドウを捕捉した可能性があるため、待機終了時に候補を再列挙し、有効性を確認するよう検証スクリプトを修正しました。

追跡処理の修正後、プロファイル選択から通常ウィンドウまでに4個の候補ハンドルが出現しました。待機終了時に有効な通常ウィンドウを再選択し、`SetWindowPos`による補正を実行できました。

| 項目 | 補正前 | 補正要求 | 補正後 |
| --- | ---: | ---: | ---: |
| X | -3609 | 100 | 100 |
| Y | -713 | 100 | 100 |
| 幅 | 3636 | 1000 | 667 |
| 高さ | 2100 | 700 | 467 |
| DPI | 144 | 96 | 96 |

プライマリディスプレイのDPIは96、使用可能領域は2560×1392でした。目視でも通常ウィンドウがプライマリディスプレイ上の要求位置付近へ移動し、要求より小さいサイズになったことを確認しました。

補正後の幅と高さは要求値のおよそ3分の2であり、DPI 144からDPI 96への比率と一致します。異なるDPIのディスプレイ間を位置とサイズの一度の操作で移動したため、ChromeがDPI変更を処理してウィンドウサイズを再調整したと判断します。

この結果を受け、最初にサイズを変えずプライマリディスプレイへ移動し、DPI変更が安定した後に要求サイズを適用する二段階補正を検証しました。

二段階補正の検証では、プロファイル選択後に通常ウィンドウが表示されたことを目視確認し、次の結果を取得しました。

| 段階 | X | Y | 幅 | 高さ | DPI |
| --- | ---: | ---: | ---: | ---: | ---: |
| 補正前 | -3609 | -713 | 3636 | 2100 | 144 |
| プライマリディスプレイへの移動後 | 100 | 100 | 2424 | 1400 | 96 |
| 最終補正後 | 100 | 100 | 1000 | 700 | 96 |
| 要求値 | 100 | 100 | 1000 | 700 | 96 |

第1段階では`SWP_NOSIZE`によりサイズを指定せず、対象ウィンドウをプライマリディスプレイへ移動しました。DPIが144から96へ変わり、測定値が安定した後、第2段階で位置とサイズを適用しました。最終的な外接矩形は要求値と一致し、目視でも想定した位置とサイズになったことを確認しました。

DWM表示境界はX=107、Y=100、幅986、高さ693でした。外接矩形との差はChromeウィンドウの不可視リサイズ境界によるものとして説明できます。MVPの「ウィンドウサイズ」はウィンドウ全体と定義しているため、判定にはPer-Monitor DPI Aware V2の呼び出し元から取得した`GetWindowRect`の外接矩形を使用します。

Chromeプロセスが0件であることを確認した未起動状態からも検証しました。起動前のChromeトップレベルウィンドウ数は0で、プロファイル選択画面から通常ウィンドウへの置き換わりを追跡できました。

| 段階 | X | Y | 幅 | 高さ | DPI |
| --- | ---: | ---: | ---: | ---: | ---: |
| 補正前 | 110 | 110 | 1100 | 770 | 96 |
| プライマリディスプレイへの移動後 | 100 | 100 | 1100 | 770 | 96 |
| 最終補正後 | 100 | 100 | 1000 | 700 | 96 |
| 要求値 | 100 | 100 | 1000 | 700 | 96 |

最終外接矩形が要求値と一致し、目視でも想定した位置とサイズであることを確認しました。これにより、Chrome未起動時と起動済み時の両方で、プロファイル選択後の通常ウィンドウを追跡して補正できることを確認しました。

敵対的レビューの指摘を反映した後、Chrome未起動状態から成功経路を再検証しました。最終候補が一意であることを確認し、ウィンドウハンドル、PID、プロセス開始時刻、ウィンドウクラスを各測定と補正の前に再照合しました。

現在のプライマリモニターは2560×1440、使用可能領域は2560×1392、移動後のウィンドウDPIは96でした。最終外接矩形はX=100、Y=100、幅1000、高さ700となり、要求した物理矩形との完全一致判定に成功しました。目視でも想定した位置とサイズであることを確認しました。

### プロファイル選択の方針

MVPではプロファイル選択画面をChromeの正常な起動フローとして許容します。アプリケーションはプロファイル情報を読み取ったり、特定または最後に使用したプロファイルを自動選択したりしません。

利用者による選択後に開く通常のブラウザウィンドウを追跡し、そのウィンドウを位置・サイズの確認と補正の対象にします。プロファイル選択の待機中は利用者が取り消せるようにし、60秒以内に選択されない場合はタイムアウトとして扱います。追跡方式と待機終了条件は、[ADR-0002](../adr/0002-track-chrome-window-lifecycle.md)で決定しています。

表示倍率を変更する場合は、ユーザーがWindowsの設定画面から行います。スクリプトはシステム設定を変更しません。

## 判定基準

- Chromeを検出でき、各起動操作で新しいトップレベルウィンドウを1つ識別できる
- 要求値と実測値の差を数値で説明できる
- 差がある場合に、DPI仮想化、ウィンドウ枠、ChromeまたはWindowsによる補正のどれが原因か切り分けられる
- 起動引数だけで要件を満たせない場合、Win32 APIによる起動後の再配置を含む代替案を比較できる

## 制約と残るリスク

- Chromiumのスイッチ定義は、Google Chromeが永続的な互換性を保証する公開APIではありません
- Chrome起動済み時は、起動したプロセスとウィンドウを所有するプロセスが一致しない可能性があります
- 複数のChromeプロファイルがある環境ではプロファイル選択画面が表示され、通常のブラウザウィンドウと同じネイティブウィンドウクラスを使用する可能性があります
- 同じ待機時間内に別のChromeウィンドウが生成された場合、タイトルや閲覧内容を取得しない現在の方式では、対象外の新規ウィンドウを候補にする可能性があります
- 待機終了時に置き換わり候補が複数残る場合、検証スクリプトは補正を行わずエラーで終了します
- プロファイル選択を完了しない場合は置き換わりを検出できないため、検証スクリプトは補正を行わずエラーで終了します
- 標準インストール先との一致だけでは実行ファイルの発行元まで保証できないため、製品実装ではデジタル署名の検証要否を決定する必要があります
- ChromeやWindowsが最小サイズ、使用可能領域、ウィンドウ枠に合わせて値を補正する可能性があります
- 100%以外の表示倍率では、呼び出し元のDPI認識状態をそろえないと比較結果を誤解する可能性があります
- Windows版GoからWSLのUNCパスにあるリポジトリを直接テストできない環境では、Windows向けテスト実行ファイルを生成して実行する必要があります
