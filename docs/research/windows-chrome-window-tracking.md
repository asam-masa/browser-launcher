# Windows 11におけるChromeウィンドウの追跡

## 目的

Chromeのプロファイル選択画面から通常のブラウザウィンドウへ遷移する過程を安全に追跡し、配置対象を決定する方式を比較します。

本調査はSCRUM-12のSpikeとして、[プロダクト要件](../product/requirements.md)と[ADR-0001](../adr/0001-control-chrome-window-on-windows.md)に残された待機と追跡の設計課題を扱います。製品コードの実装は対象外です。

## 明らかにしたい問い

1. ウィンドウの生成、表示、破棄をどのように検知するか
2. プロファイル選択画面と選択後の候補をどのように関連付けるか
3. 他のChromeウィンドウを誤操作しないために何を確認するか
4. イベントの欠落、競合、ハンドルの再利用へどう対処するか
5. 利用者がプロファイルを選択しない場合に、待機をどう終了するか

## 一次情報から確認した事実

### WinEventフック

Windowsの`SetWinEventHook`は、指定した範囲のアクセシビリティイベントを受け取るAPIです。`WINEVENT_OUTOFCONTEXT`では、コールバックを発生元プロセスへ読み込まず、イベントを非同期のキューとして順番に配信します。

利用にあたって次の制約があります。

- フックを登録したスレッドにはメッセージループが必要である
- Out-of-contextのイベントは、フックを登録したスレッドへ配信される
- コールバック処理中にも別のイベントが発生して再入する可能性がある
- マネージドコードでは、コールバックが移動または回収されないよう保持する必要がある
- `UnhookWinEvent`はフックを登録したスレッドから呼び出す必要がある

したがって、コールバックでは受信値をキューへ追加するだけにし、候補の検証や状態遷移はコールバック外で逐次処理します。

### 対象イベント

トップレベルウィンドウの遷移を観測するため、次のイベントを候補とします。

| イベント | 値 | 用途 |
| --- | ---: | --- |
| `EVENT_OBJECT_CREATE` | `0x8000` | ウィンドウ候補の生成を知る |
| `EVENT_OBJECT_DESTROY` | `0x8001` | 候補が無効になった可能性を知る |
| `EVENT_OBJECT_SHOW` | `0x8002` | 非表示だった候補の表示を知る |

`idObject == OBJID_WINDOW`かつ`idChild == CHILDID_SELF`のイベントだけを入口とし、有効なハンドルは`GetAncestor(GA_ROOT)`でトップレベルウィンドウへ正規化します。

破棄イベントを受け取った時点では対象オブジェクトへ問い合わせられません。また、イベントの受信だけでは、そのウィンドウがChromeの通常ウィンドウであることや、今回の起動操作に属することを証明できません。

### Chromeのプロファイル選択

Chromiumの実装には、Chromeの起動時だけでなく、既存プロセスで新しいセッションを開始した場合にもプロファイル選択画面を表示する経路があります。既存のプロファイル選択画面を再利用する場合もあります。

実機検証では、プロファイル選択画面と通常のブラウザウィンドウが同じ`Chrome_WidgetWin_1`クラスを使用しました。ウィンドウタイトル、クラス名、起動したプロセスIDのいずれか1つだけで両者を安全に区別する設計にはできません。

## 方式の比較

### Option 1: WinEventだけで追跡する

利点:

- 変化を低遅延で検知できる
- 一定間隔の全ウィンドウ列挙を減らせる

欠点:

- イベントは候補の意味や今回の起動操作との因果関係を保証しない
- フック登録前の変化や、処理時点ですでに無効なハンドルを扱えない
- Chromeのマルチプロセス構成により、起動時のPIDだけでは絞り込めない

### Option 2: ポーリングだけで追跡する

利点:

- 毎回のスナップショットを同じ検証手順で扱える
- メッセージループとコールバックの管理が不要である

欠点:

- 間隔より短い生成と消失を観測できない
- 間隔を短くすると、不要な列挙が増える
- 変化がない期間も列挙を繰り返す

### Option 3: WinEventとポーリングを併用する

WinEventを再スナップショットの契機として使い、低頻度のポーリングを再同期とタイムアウト判定に使います。

利点:

- 変化へ早く反応しつつ、現在の状態をWin32 APIで再確認できる
- イベントの欠落、競合、一時的なハンドルへポーリングで対処できる
- イベントとスナップショットの責務を分離できる

欠点:

- フック、メッセージループ、ポーリングのライフサイクル管理が必要である
- 単独方式よりテスト対象が増える

## 推奨方式

Option 3のハイブリッド方式を推奨します。WinEventは「状態が変わった可能性」の通知に限定し、配置対象の決定には使用しません。

### 追跡手順

1. 起動前のChromeトップレベルウィンドウをスナップショットとして保存する
2. Out-of-contextのWinEventフックを登録し、メッセージループの開始を確認する
3. Chromeへ新規ウィンドウの起動を要求する
4. 対象イベントまたはポーリング間隔の到達時に、Chromeトップレベルウィンドウを再列挙する
5. 起動前に存在しなかった候補と、その出現、非表示、消失の遷移を記録する
6. 候補が安定した時点で、ハンドル、PID、プロセス開始時刻、クラス、可視性を再確認する
7. 有効な新規候補が1つに確定した場合だけ、配置処理へ渡す
8. 完了、取消、タイムアウト、失敗のいずれでも、登録元スレッドでフックを解除する

イベント順だけで「プロファイル選択済み」と断定しません。起動前との差分から現れた候補が置き換わり、待機終了時に有効な候補が1つだけ残ることを、今回の起動操作に対応するための必要条件とします。複数候補が残る場合や同一性を再確認できない場合は、安全側に倒して配置しません。

### 状態モデル

| 状態 | 意味 | 次の主な状態 |
| --- | --- | --- |
| `Idle` | 起動操作前 | `Observing` |
| `Observing` | フックと初期スナップショットの準備完了 | `WaitingForSelection`, `CandidateObserved`, `Failed` |
| `WaitingForSelection` | 遷移後の候補を待機中 | `CandidateObserved`, `Cancelled`, `TimedOut`, `Failed` |
| `CandidateObserved` | 新規候補を検出したが未確定 | `CandidateValidated`, `WaitingForSelection`, `Failed` |
| `CandidateValidated` | 一意性と同一性を確認済み | 配置処理 |
| `Cancelled` | 利用者が待機を取り消した | `Idle` |
| `TimedOut` | 最大待機時間に達した | `Idle` |
| `Failed` | 追跡の安全性を確認できない | `Idle` |

## 待機終了条件の選択肢

### Option A: 利用者の取消だけで終了する

プロファイルが選択されるか、利用者が取り消すまで待機します。

- 利点: 選択に時間がかかっても操作を継続できる
- 欠点: 取消操作が行われないと、フックと待機状態が残り続ける

### Option B: 固定タイムアウトだけで終了する

一定時間で自動的に失敗へ遷移します。

- 利点: リソースの解放時点が明確である
- 欠点: 利用者の選択速度や環境差により、正常な操作を途中で終了する可能性がある

### Option C: 利用者の取消と最大待機時間を併用する

待機中は利用者が取り消せるようにし、取り消されない場合も設定済みの最大時間で終了します。

- 利点: 利用者の制御とリソース解放の上限を両立できる
- 欠点: 最大待機時間と、タイムアウト時の表示を決める必要がある

Option Cを採用します。最大待機時間は60秒とし、タイムアウトは成功として扱わず、入力を保持した再実行可能な状態へ戻します。

## 検証方法

[`verify-chrome-window-events.ps1`](../../scripts/spike/verify-chrome-window-events.ps1)は、WinEventと定期スナップショットを観測するためのスクリプトです。

このスクリプトはChromeを起動、移動、リサイズせず、次の情報だけをJSONで出力します。

- CREATE、DESTROY、SHOWの受信時刻とハンドル
- Chromeトップレベルウィンドウのハンドル、PID、プロセス開始時刻、クラス、可視性
- イベントまたはポーリングによってスナップショットを取得した理由

ポーリングは指定間隔で継続しますが、JSONには初期状態、対象イベントを受信した時点、またはChromeウィンドウのスナップショットが変化した時点だけを記録します。

ウィンドウタイトル、Chromeプロファイル、閲覧内容、実行ファイルの絶対パスは取得しません。

Windows PowerShellでリポジトリのルートへ移動し、観測を開始します。

```powershell
.\scripts\spike\verify-chrome-window-events.ps1 -ObserveSeconds 30
```

観測中に、別の操作でChromeの起動とプロファイル選択を行います。

明示的な取消経路を検証する場合は、観測時間より短い`CancelAfterSeconds`を指定します。

```powershell
.\scripts\spike\verify-chrome-window-events.ps1 -ObserveSeconds 30 -CancelAfterSeconds 10
```

JSONには`Outcome`、`HookRegistered`、`UnhookSucceeded`を出力します。`Outcome`は通常完了時に`Completed`、明示的な取消時に`Cancelled`となります。登録したフックの解除に失敗した場合、スクリプトはエラーで終了します。

タイムアウト経路を検証する場合は、観測時間より短い`TimeoutAfterSeconds`を指定します。

```powershell
.\scripts\spike\verify-chrome-window-events.ps1 -ObserveSeconds 75 -TimeoutAfterSeconds 60
```

指定時間に到達した場合、`Outcome`は`TimedOut`となります。

## テストマトリクス

| ID | Chromeの開始状態 | 操作 | 確認すること | 結果 |
| --- | --- | --- | --- | --- |
| T-01 | 未起動 | Chromeを起動しプロファイルを選択 | 選択画面から通常ウィンドウまでのイベントと差分 | 通常ウィンドウまで追跡成功 |
| T-02 | 起動済み | 新規ウィンドウを要求しプロファイルを選択 | 既存ウィンドウを候補から除外できるか | 通常ウィンドウまで追跡成功 |
| T-03 | 起動済み | 選択中に別のChromeウィンドウを開く | 複数候補を成功扱いしないか | 競合状態を2回再現 |
| T-04 | 任意 | プロファイルを選択しない | 取消と最大待機時間で終了できるか | 60秒でタイムアウト成功 |
| T-05 | 任意 | 遷移中の候補を閉じる | 無効なハンドルを配置対象にしないか | 候補の破棄と消失を確認 |
| T-06 | 任意 | 観測を中断する | 登録元スレッドでフックを解除できるか | 取消後の解除と再登録に成功 |

### 検証履歴

Chromeのトップレベルウィンドウが存在する状態で、WinEventと500ミリ秒間隔のスナップショットを45秒間観測しました。

| 段階 | Chromeトップレベルウィンドウのハンドル | 確認した変化 |
| --- | --- | --- |
| 観測開始 | `197644`, `265270` | 起動前から存在 |
| 遷移中 | `197644`, `265270`, `592918` | 一時候補が出現 |
| 置き換わり | `197644`, `265270`, `855096` | 新しい候補が出現し、一時候補が破棄 |
| 遷移後 | `197644`, `855096` | `265270`が破棄され、既存候補と新規候補が残存 |

候補`197644`は観測中に変化せず、既存ウィンドウとして差分から除外できました。プロファイル選択に伴う候補の出現と破棄はWinEventで検知でき、各イベント後の`EnumWindows`でも現在の候補を再確認できました。

この結果は、WinEventを変化の通知、スナップショットを現在状態の確認に使うハイブリッド方式を支持します。最終候補は、目視確認により通常のChromeブラウザウィンドウであることを確認しました。

一方、ハンドル、PID、クラス、可視性だけでは、最終候補が通常のブラウザウィンドウであることを機械的に証明できません。製品実装では、追跡できたことと画面種別を判定できることを区別します。

Chromeプロセスが0件であることを確認した未起動状態からも、WinEventと500ミリ秒間隔のスナップショットを60秒間観測しました。

| 段階 | Chromeトップレベルウィンドウのハンドル | 確認した変化 |
| --- | --- | --- |
| 観測開始 | なし | ChromeプロセスとChromeウィンドウは0件 |
| プロファイル選択 | `984328` | 最初のChromeトップレベルウィンドウが出現 |
| 選択後 | `329732`, `984328` | 新しい候補が出現 |
| 遷移後 | `329732` | `984328`が破棄され、新しい候補だけが残存 |

最終候補`329732`は観測終了まで残り、目視確認により通常のChromeブラウザウィンドウであることを確認しました。Chrome未起動時にも、プロファイル選択画面に対応する候補の出現と破棄、および通常ウィンドウに対応する候補の残存を追跡できました。

候補競合の検証では、プロファイル選択中に既存のChromeウィンドウから別の通常ウィンドウを開き、その後にプロファイルを選択しました。1回目は観測終了時に4件の新規候補が残り、目視でも複数の通常Chromeウィンドウを確認しました。

再検証では、起動前から存在した候補1件をスナップショットとして保持し、起動前との差分を確認しました。

| 項目 | 結果 |
| --- | --- |
| 起動前の候補 | 1件 |
| 同時に存在した新規候補の最大数 | 3件 |
| 観測終了時に残った新規候補 | 2件 |
| 起動前候補の残存 | 確認 |
| 複数の通常ウィンドウの目視確認 | 確認 |

2回の検証で、起動前との差分だけでは配置対象を一意に決定できない競合状態を再現しました。新規候補が複数残る場合は候補を選択せず、明示的な競合エラーとして配置処理へ進まないものとします。検証スクリプトは観測専用であるため、拒否判定の自動テストは製品実装時に行います。

候補消失の検証では、プロファイル選択画面を表示した後、プロファイルを選択せずに画面を閉じました。

| 項目 | 結果 |
| --- | --- |
| 起動前の候補 | 0件 |
| 新規候補の最大数 | 1件 |
| 観測した候補 | `1051658` |
| 観測したイベント | CREATE、SHOW、DESTROY |
| 観測終了時の新規候補 | 0件 |
| 通常ウィンドウが開かなかったことの目視確認 | 確認 |

破棄された候補は後続のスナップショットから消失し、配置対象として残りませんでした。候補が消失した場合は成功扱いせず、配置処理へ進みません。

製品実装では、利用者がプロファイル選択画面を閉じた取消と、OSまたはChrome側の理由による予期しない候補消失を別の結果として扱います。WinEventとウィンドウ状態だけでは終了理由を断定できないため、利用者がアプリケーション上で取消を指示した事実と組み合わせて判定します。

取消時の後始末では、30秒の観測を10秒後に自己取消する明示的な取消経路を検証しました。

| 実行 | Outcome | HookRegistered | UnhookSucceeded |
| --- | --- | --- | --- |
| 10秒後に取消 | `Cancelled` | `true` | `true` |
| 取消直後に3秒間再観測 | `Completed` | `true` | `true` |

取消時に登録元スレッドからフックを解除し、その直後にもフックを再登録して正常終了できました。

WSLの端末からWindows PowerShellへCtrl+Cを送る方法では、入力がWindows側へ伝達されませんでした。この実行は検証結果に含めません。端末の割り込み伝達は実行環境に依存するため、製品実装ではUI操作から明示的な取消シグナルを発行し、同じ後始末経路へ接続します。

タイムアウト検証では、Chromeウィンドウが0件の状態からプロファイル選択画面を表示し、プロファイルを選択せずに待機しました。

| 項目 | 結果 |
| --- | --- |
| 最大待機時間 | 60秒 |
| 観測した候補 | `788784` |
| 観測中の最大候補数 | 1件 |
| タイムアウト時の候補数 | 1件 |
| Outcome | `TimedOut` |
| HookRegistered | `true` |
| UnhookSucceeded | `true` |
| 画面種別の目視確認 | プロファイル選択画面 |

プロファイル選択画面が残った状態でも、60秒で成功扱いせずに待機を終了し、登録元スレッドからフックを解除できました。

## 制約と残るリスク

- WinEventは、イベントと利用者が開始した起動操作の因果関係を提供しない
- Chromeの内部実装変更により、ウィンドウの生成順やクラスが変わる可能性がある
- 同時に別のChromeウィンドウが開かれた場合、プライバシー情報を読まずに候補を一意にできない可能性がある
- ウィンドウハンドルは再利用され得るため、PIDとプロセス開始時刻を含む同一性の再確認が必要である
- イベントの受信時刻は順序の補助情報としてのみ使い、異なるクロックとの経過時間比較には使わない
- 60秒の最大待機時間が利用者の実際の操作に十分かは、製品のユーザビリティテストでも確認する必要がある
